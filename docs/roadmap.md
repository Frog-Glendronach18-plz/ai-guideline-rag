# 生成AIデモ 週末ロードマップ

Oct 8, 2026 · @カエル

## ゴールと方針

日曜夜までに「AI事業者ガイドラインに出典付きで答えるRAG Q&A」を公開する。版の差分への回答とファクトチェックはオン／オフ付きの追加機能とし、本体だけでも公開できる状態を常に保つ。

- 作るもの：AI事業者ガイドライン（第1.1版・第1.2版）に質問すると、回答と「版＋ページ番号」を返すWebアプリ
- 追加機能1（版の差分）：「第1.2版で何が変わった？」のような差分の質問に、両方の版の該当箇所を並べて答える
- 追加機能2（ファクトチェック）：回答の主張をWeb検索で照合し、さらに新しい版や公式情報と食い違っていないかを表示する
- 方針：小さく作って動かしてから足す。どちらの追加機能もまず固定ワークフローで作り、エージェント化は週末以降に回す
- 位置づけ：主目的はAIフレームワークの学習。サブはデプロイとCIまで
- 想定ユースケース：社内規程や業界ガイドラインの改訂時に「何が変わったか」「自社に関係する箇所はどこか」を確認する作業の効率化
- LangChainは初めてなので、公式ドキュメントの最新チュートリアル（**v1系**）を正とする。v1でAPIが大きく変わったため、v0.x時代の記事のコードは動かないことが多い

## 題材

総務省・経済産業省「AI事業者ガイドライン」の本編を使う。別添は分量が多いため週末は対象外とし、拡張で追加する。

| 版 | 公表日 | 用途 |
| --- | --- | --- |
| 第1.1版 本編 | 2025年3月28日 | 旧版として索引に入れる |
| 第1.2版 本編 | 2026年3月31日 | 最新版として索引に入れる |
| 第1.2版 本編（第1.1版からの変更履歴付き） | 2026年3月31日 | **索引には入れない**。差分の質問の正解データとして評価に使う |

題材に選んだ理由：公式の変更履歴付きの版があるため差分の正解を作りやすいこと、改訂の中心がAIエージェントやフィジカルAIの追加でAIコンサルのテーマに直結すること。

## 技術構成

すべてPythonで組む。DBサーバーは立てず、索引はローカルで事前に作ってファイルとしてリポジトリに含める。

| 役割 | 採用 | 補足 |
| --- | --- | --- |
| フレームワーク | LangChain v1（`langchain` / `langchain-anthropic` / `langchain-cloudflare`） | 拡張でLangGraphへ |
| LLM | Claude Haiku 5.5（`claude-haiku-5-5`。回答品質が足りなければ Sonnet 5.5） | Haiku 5.5 は入力$0.10／出力$0.50（100万トークンあたり）でHaiku 4.5の1/10。振り分け・抽出は effort を low にする |
| 埋め込み | Cloudflare Workers AI `bge-m3`（REST API経由） | ClaudeのAPIには埋め込みがないため別途必要。無料枠（1日1万Neurons ≒ 約900万トークン）で足り、日本語対応 |
| ベクトルストア | LangChainの `InMemoryVectorStore`（`dump`/`load` でファイル保存） | ネイティブ依存なし・省メモリ。版の絞り込みはメタデータのフィルタで行う。足りなくなったらFAISSへ |
| Web検索 | Tavily（LangChain連携あり、無料枠） | ファクトチェック用 |
| UI | Gradio | Pythonだけで画面が作れる |
| 公開先 | Render 無料Web Service | 0円。GitHub連携＋`requirements.txt`＋起動コマンドだけ。Docker不要 |
| CI/CD | GitHub Actions（ruff＋pytest）→ Render自動デプロイ | mainへのpushで自動デプロイ（CD）。CIは「できれば」 |
| Python | 3.12 の仮想環境 | ローカルは3.14だが、ライブラリの対応待ちでハマらないよう本番と揃える |

費用の見込み：新たに払うのはClaude APIの前払いクレジット（最低5ドル程度）だけ。Claude Proの月額にはAPI利用料が含まれないため別途必要。埋め込み（Workers AI）、Web検索（Tavily）、公開（Render）は無料枠に収める。

公開先の選定メモ（2026年10月時点）：Hugging Face Spacesは2026年夏から新規のGradio SpaceにPRO（有料）が必要になり、無料のZeroGPU枠はアカウント作成30日以上が条件のため見送り。Cloudflareは通常のWorkersではGradioが動かず、Containersは月5ドル＋Docker学習が必要なため見送り（拡張候補）。

```mermaid
flowchart LR
  subgraph 事前（ローカル）
    PDF[第1.1版・第1.2版 本編] --> Split[版・ページ番号付きで分割] --> Emb[埋め込み] --> Index[(index.json)]
  end
  subgraph 本番（Render）
    Q[質問] --> Route{質問の種類を判定}
    Route -->|単一の版| Ret1[指定版（既定は最新版）から上位k件]
    Route -->|差分| Ret2[版ごとに上位k件ずつ]
    Ret1 --> LLM[Claudeで回答＋出典]
    Ret2 --> LLM
    LLM --> Show[回答を表示]
    Index -.起動時に読み込み.-> Ret1
    Index -.-> Ret2
    Show -.-> FC
    subgraph FC[ファクトチェック（オン／オフ）]
      Claims[主張を最大3つ抽出] --> Search[Tavily検索] --> Judge[一致／食い違い／不明を判定]
    end
  end
```

回答は「回答を表示」の時点で利用者に返し、点線内のファクトチェックはその後に追記する。差分の経路やファクトチェックが止まっても、「単一の版」の経路だけでデモは成立する。

## Phase 1（土曜）：LangChain入門とRAG本体

土曜の終わりに、ノートブック上で「質問すると版＋出典ページ付きで答える」状態にする。UIや公開はまだやらない。

**午前：LangChainに慣れる**

- [x] 公式の入門チュートリアルを写経する（`create_agent` のクイックスタートで、ツール呼び出しのメッセージの流れを確認）
- [x] 練習スクリプトで部品を試す（`scripts/hello_lang.py`：チャットモデルの呼び出し、プロンプトテンプレートとチェーン、参照テキストの有無での回答の比較）
- [x] 構造化出力を一度試す（回答・根拠ページ・回答可否をPydanticモデルで返させる。参照テキストにない質問では `answerable: False` になることを確認）

**午後：RAGを組む**

- [x] 2つの版のPDFを読み込み、メタデータに `version`（"1.1" / "1.2"）と印刷されたページ番号を持たせる（`loader.py`。`PyPDFLoader` は `langchain-community` の開発終了予定とページ番号のずれのため使わず、`pypdf` で直接読む）
- [x] テキストを `unicodedata.normalize("NFKC", ...)` で正規化する（あわせて和文の途中の折り返しをつなげる）。第1.1版のPDFは「⽉」「⽤」などの康煕部首（見た目は同じだが別の文字）が混ざっており、そのままだと検索や差分比較がずれる
- [x] `RecursiveCharacterTextSplitter` でチャンク分割する。**区切り文字に「。」「、」を追加する**（既定は英語向けで、日本語だと文の途中で切れる）。`keep_separator="end"` で句点を文末に残し、見出しだけの短いチャンクは次のチャンクに結合（`splitter.py`。600文字・重なり100で252チャンク、評価用5問の正解の文はすべて1チャンクに収まる）
- [ ] 埋め込みを作って `InMemoryVectorStore` に入れ、`dump` でファイル保存する（`build_index.py` として切り出す）
- [ ] 保存した索引を `load` し、版を最新版に絞り込んだうえでRetrieverで上位k件を取り、プロンプトに入れて回答させる
- [ ] 回答に出典を付ける（構造化出力で「回答」「使った版とページ番号」を返させる）
- [ ] 単一の版への質問3問を流し、明らかにおかしい回答がないか目で確認する

ここまで動けば、日曜に何かが間に合わなくても公開できるデモの芯ができている。

## Phase 2（日曜午前）：版の差分 → ファクトチェック

まず版の差分への回答を足し、時間が残ればファクトチェックを足す。差分の方を先にするのは、索引の中だけで完結して外部APIが増えず、メタデータでの絞り込みや質問の振り分けといったLangChainの基本を練習できるため。どちらも最初からオン／オフのスイッチを付けて作る。

**版の差分（優先）**

- [ ] 質問の種類を判定する：構造化出力で「単一の版（どの版か）」か「差分」かを返させる
- [ ] 差分の質問では、版ごとにフィルタを付けて上位k件ずつ取り、「第1.1版の該当箇所」「第1.2版の該当箇所」として区別してプロンプトに入れる
- [ ] 回答形式を決める：変更点ごとに「旧（1.1）／新（1.2）／変更の要点」と、それぞれの出典ページを示す
- [ ] 片方の版にしか該当箇所がない場合は「新設」「削除」の可能性として扱い、断定しないようプロンプトで指示する
- [ ] 差分の質問2問を流し、変更履歴付きPDFと照らし合わせて確認する

**ファクトチェック（時間が残れば）**

- [ ] 回答から検証すべき主張を最大3つ抜き出す（構造化出力でリストとして返させる）
- [ ] 主張ごとにWeb検索を1回だけ実行する（TavilyのLangChain連携）
- [ ] LLMが主張ごとに「一致／食い違い／不明」を判定し、参照URLを付ける
- [ ] 公式ドメイン（`meti.go.jp`、`soumu.go.jp`）の結果を優先するよう、検索条件（`include_domains` など）で指定する
- [ ] 主張数・検索回数・最大トークンに上限を設ける（コストとレイテンシの対策）

昼の時点で動いていない機能はスイッチをオフにしてPhase 3へ進む。

## 完了条件と割り切り

最低ラインは「RAG本体（単一の版への出典付き回答）が公開URLで動き、READMEがある」こと。それ以外は削ってよい。

| 優先度 | 内容 | 遅れたときの判断 |
| --- | --- | --- |
| 必須 | RAG本体（版＋ページの出典付き回答）、悪用対策、公開、README | 削らない |
| できれば（優先） | 版の差分への回答 | スイッチをオフにして公開し、README内で「開発中」と書く |
| できれば | ファクトチェック | 同上 |
| できれば | チャンクサイズ比較の評価表 | 1通りだけの正答数を載せる |
| できれば | CI（GitHub Actions） | 自動デプロイ（CD）だけで公開する |
| やらない | 別添の取り込み、PDFアップロード機能、会話履歴、エージェント化 | 週末以降に回す |

## 週末以降の拡張

週末のデモを土台に、1テーマずつ足していく。上から順に、学びが大きい順に並べている。

1. 評価を強化する：質問を20問以上に増やし（差分の質問は変更履歴付きPDFから網羅的に作る）、LLM-as-a-judgeやRagas系の指標で自動評価する
2. 検索を改善する：ハイブリッド検索（キーワード＋ベクトル）とリランキングを入れ、評価表で効果を比較する
3. 全文投入と比較する：2つの版の本文（約7万トークン）をそのまま渡す方式とRAGで、正答率・出典の正確さ・1問あたりのコスト・応答時間を比べる
4. 差分とファクトチェックをエージェント化する：「どの版を検索するか」「クエリの言い換え」「再検索するか」「Web検索が必要か」をLLMに判断させる（LangGraph）
5. 題材を広げる：別添を取り込む、第1.0版・第1.01版を加えて改訂の流れを追えるようにする
6. 運用まわりを追加する：トレーシング（Langfuseなど）、コストとレイテンシの計測、プロンプトインジェクション対策
7. ベクトルDBをpgvectorに置き換える
8. Cloudflareをさらに使う：独自ドメインをCloudflareで管理してRenderに向ける、ベクトルストアをVectorizeに移す、またはCloudflare Containers / Python Workersへの移植を試す
