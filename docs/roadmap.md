## ゴールと方針

「AI事業者ガイドラインに出典付きで答えるRAG Q&A」を公開し、版の差分への回答と評価を足していく。本体だけでも公開できる状態を常に保つ。

- 作るもの：AI事業者ガイドライン（第1.1版・第1.2版）に質問すると、回答と「版＋ページ番号」を返すWebアプリ
- 追加機能1（版の差分）：「第1.2版で何が変わった？」のような差分の質問に、両方の版の該当箇所を並べて答える
- 追加機能2（ファクトチェック）：回答の主張をWeb検索で照合する（優先度は低い）
- 方針：小さく作って動かしてから足す。追加機能はまず固定ワークフローで作り、エージェント化は後に回す
- 位置づけ：主目的はAIフレームワーク（LangChain）の学習。サブはデプロイとCIまで
- 時間の使い方：Gradio の画面（`app.py`）とデプロイは試作を見せるための手段として深掘りしない。実務の本番は AWS など別の構成になるため、「本番ならこう作る」を README に整理するに留め、評価と LangChain での処理の組み立てに時間を割く
- 想定ユースケース：社内規程や業界ガイドラインの改訂時に「何が変わったか」「自社に関係する箇所はどこか」を確認する作業の効率化
- LangChain は公式ドキュメントの最新（**v1系**）を正とする。v0.x時代の記事のコードは動かないことが多い

## 技術構成

すべてPythonで組む。DBサーバーは立てず、索引はローカルで事前に作ってファイルとしてリポジトリに含める。

| 役割 | 採用 | 補足 |
| --- | --- | --- |
| フレームワーク | LangChain v1（`langchain` / `langchain-anthropic` / `langchain-cloudflare`） | 拡張でLangGraphへ |
| LLM | Claude Haiku 5.5（`claude-haiku-5-5`。回答品質が足りなければ Sonnet 5.5） | 入力$0.10／出力$0.50（100万トークンあたり）でHaiku 4.5の1/10 |
| 埋め込み | Cloudflare Workers AI `bge-m3`（REST API経由） | 無料枠（1日約900万トークン）で足り、日本語対応。選定理由は `embeddings.py` |
| ベクトルストア | LangChainの `InMemoryVectorStore`（JSONで保存、全件比較） | 252チャンクなら十分速い。版の絞り込みはメタデータのフィルタ |
| Web検索 | Tavily（LangChain連携あり、無料枠） | ファクトチェック用（未着手） |
| UI | Gradio | Pythonだけで画面が作れる。試作用 |
| 公開先 | Render 無料Web Service | 0円。GitHub連携、`uv.lock` があれば uv が使える。Docker不要 |
| CI/CD | GitHub Actions（ruff＋pytest）→ Render自動デプロイ | CD（mainへのpushで自動デプロイ）は稼働中。CIは「できれば」 |
| Python | 3.12（uv で管理） | ローカルは3.14だが、ライブラリの対応待ちでハマらないよう本番と揃える |

費用：新たに払うのはClaude APIの前払いクレジット（5ドル程度、利用上限額を設定済み）だけ。Claude Proの月額にはAPI利用料が含まれない。埋め込み・Web検索・公開は無料枠に収める。

公開先の選定メモ（2026年10月時点）：Hugging Face Spacesは2026年夏から新規のGradio SpaceにPRO（有料）が必要になり、無料のZeroGPU枠はアカウント作成30日以上が条件のため見送り。Cloudflareは通常のWorkersではGradioが動かず、Containersは月5ドル＋Docker学習が必要なため見送り（拡張候補）。

```mermaid

  subgraph 事前（ローカル）
    PDF[第1.1版・第1.2版 本編] --> Split[版・ページ番号付きで分割] --> Emb[埋め込み] --> Index[(index.json)]
  end
  subgraph 本番（Render）
```

## 次にやること

### ① 版の差分（LangChain の学習の本題）

差分の質問に答えられるようにする。索引の中だけで完結し、質問の振り分けや版での絞り込みといった、LangChain で処理を組み立てる練習になる。

- [ ] 質問の種類を判定する：構造化出力で「単一の版（どの版か）」か「差分」かを返させる
- [ ] 検索用のクエリを書き換える：質問が章番号など文書の構造を指していて本文の言葉を含まない場合（D2）に、LLMに検索用の言葉を作らせる。D2のヒット率が改善するかを確かめる
- [ ] 差分の質問では、版ごとに上位k件ずつ取り（`search_each_version()`）、「第1.1版の該当箇所」「第1.2版の該当箇所」として区別してプロンプトに入れる
- [ ] 回答形式を決める：変更点ごとに「旧（1.1）／新（1.2）／変更の要点」と、それぞれの出典ページを示す
- [ ] 片方の版にしか該当箇所がない場合は「新設」「削除」の可能性として扱い、断定しないようプロンプトで指示する
- [ ] 画面の版の選択に「差分」を加え、差分の質問の例を置く
- [ ] 差分の質問2問を流し、変更履歴付きPDFと照らし合わせて確認する

### ② 評価（ポートフォリオとして一番見せたいところ）

「作った」より「測って改善した」を示す。

- [ ] `scripts/eval.py`：評価用の質問を流し、正答（`must_include` のキーワード）・出典の一致・回答可否・1問あたりのトークン数とコスト・応答時間を表にする
- [ ] 質問を増やす（目安20問。差分の質問は変更履歴付きPDFから網羅的に作る）
- [ ] チャンク長の比較を、増やした質問でやり直す
- [ ] 差分の質問：変更点をいくつ拾えたか・誤った変更点を挙げていないかを記録する

検索のみの事前比較（Oct 10、`try_search.py`。正解判定6件、LLMなし）：

| チャンク長 | 件数 | top1 | top3 | top5 | top10 |
| --- | --- | --- | --- | --- | --- |
| 300 | 480 | 3 | 4 | 4 | 4 |
| 600 | 252 | 3 | 3 | 4 | 4 |
| 1000 | 156 | 2 | 3 | 3 | 3 |

1000文字は悪化傾向（長いチャンクは複数の話題が混ざりベクトルがぼやける）。300と600の差は1問分で誤差の範囲のため600を維持し、検索件数は5件に。重なりの割合は300と600でほぼ同じ（20%と17%）で、差の要因ではない。判定6件では結論が弱いので、質問を増やして比べ直す。D2はどの長さでも圏外（質問の形の問題）。詳しくは `scripts/try_search.py` のメモ。
